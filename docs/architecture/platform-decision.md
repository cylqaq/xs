# 平台决策：Cursor OS vs 本地 Web

> 不考虑时间成本，只论**长期稳定**与**终极流水线通用性**。

## 结论（先给）

| 维度 | 更优方案 |
|------|----------|
| **流水线与数据 10 年可移植** | **Canon 文件系统 + `forge` CLI**（两者共用） |
| **多本书管理、进度、续写 UX** | **本地 Web 控制台** |
| **单章创作质量上限、Agent 能力** | **Cursor（或同类 Agent IDE）作算力插件** |
| **若只能二选一** | **本地 Web 为主壳 + Cursor 打开同一 `stories/` 深写** |

纯 Cursor-only 适合「作者即开发者、单书、接受 IDE 当 UI」。  
你的目标（多书、随时进度、随时续写、通用流水线）长期更匹配 **Web 控制平面**。

## 对比矩阵

|  | Cursor OS 交互 | 本地 Web 项目 |
|--|----------------|---------------|
| **记忆真相源** | ✅ 已是文件 Canon | ✅ 同一 Canon，无第二模型 |
| **多书切换** | ⚠️ 靠文件夹，无可视化 | ✅ 书架、进度条、债务仪表 |
| **续写断点** | ⚠️ 依赖会话/人工记路径 | ✅ writing-plan + 一键续写 |
| **图谱/伏笔/追读力** | ⚠️ 读 YAML，无全景 | ✅ 天然可视化 |
| **规则评审 forge** | ✅ 终端即可 | ✅ Web 调 CLI 展示结果 |
| **Agent 写作质量** | ✅ 原生 Harness/Skill | ⚠️ 需接 API/SDK，要维护 |
| **厂商锁定** | ❌ 绑 Cursor 路线图 | ✅ 自有应用 |
| **家人/协作** | ❌ 难 | ✅ 可扩展 |
| **离线** | ⚠️ 视模型 | ✅ 文稿本地；生成可离线读 |
| **维护负担** | ✅ 低 | ❌ 前后端长期维护 |

## 推荐终态架构

```
┌─────────────────────────────────────┐
│  本地 Web（控制平面）                  │
│  书架 · 进度 · 图谱 · 债务 · 触发续写   │
└──────────────┬──────────────────────┘
               │ 只读写 stories/
┌──────────────▼──────────────────────┐
│  novel-forge 核心（与 UI 无关）        │
│  stories/ · harness/ · skills/ · forge│
└──────────────┬──────────────────────┘
               │ 可选
┌──────────────▼──────────────────────┐
│  Cursor / SDK Agent（算力平面）       │
│  深写、精修、复杂编排                   │
└─────────────────────────────────────┘
```

**原则**：Web 不做「第二套小说数据库」；只做 Canon 的视图与流水线按钮。

## 为何不是「只 Cursor」

1. 你要的「任意本数、随时进度」是 **产品能力**，不是 IDE 能力。  
2. 终极流水线的稳定锚是 **协议（目录+CLI）**，不是聊天窗口。  
3. Cursor 变强/变贵/策略变化时，Canon+CLI 仍存活；Web 可换 Agent 后端。

## 为何不是「只 Web」

1. 高质量正文生成仍依赖强 Agent；Cursor 当前仍是最高效 Harness。  
2. Skills 在 IDE 内迭代更快。  
3. 故：**Web 管书，Cursor 管深写** 长期最稳。
